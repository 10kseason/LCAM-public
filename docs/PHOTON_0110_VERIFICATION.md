# PHOTON 0.11.0 SER Night 구현과 검증

2026-10-23. 로컬 개발 후보 `0.11.0-ser-night`, 코드 17의 기록입니다. 이전 비공개 GitHub·Drive 0.10.0 배포는 변경하지 않았습니다. 빌드·설치·합성 검사·사용자 실촬영 검증은 서로 다른 상태로 구분합니다.

## 동작과 선택 이유

이전에는 SER가 별도 Python 정책 실험뿐이었습니다. 이 버전은 홈·AUTO 설정에서 별도 SER Night 카메라를 열고 후면 1배 RAW 세션을 미리 연결합니다. 셔터 때 CameraX/Camera2를 전환하지 않도록 세션을 유지하며 기존 AUTO·RAW DNG 처리와 분리했습니다. 출력은 전체 4080x3060(12.4848MP), 4:3으로 크기를 바꾸지 않으며 와이드·시네마 자르기는 적용하지 않습니다.

최신의 안정된 초점·노출·WB를 고정하고 같은 노출 RAW를 최대 3장 요청합니다. 노출은 50ms 이하로 제한하고 물리 센서 범위 안에서 ISO로 보상합니다. 이는 획득 시간을 제한하기 위해 노출 시간을 게인과 맞바꾸는 것이며 추가 광자 정보를 얻는다는 뜻이 아닙니다. ISO 상한 때문에 더 어두워질 수 있습니다. 보수적인 요청 허용 검사는 단일 프레임으로 돌아갈 수 있습니다. 완전한 RAW·결과 쌍과 실제 자동 미리보기 복원 결과가 있어야 다음 촬영을 허용합니다. 동시 작업 2개·공통 처리 잠금으로 메모리를 제한하며 가득 찬 대기열은 준비를 늦출 수 있습니다.

네이티브 준비는 Bayer 짝수 이동을 정렬하고 움직임·구조·노이즈 일치를 추정합니다. GLES3.1은 세 단계로 합성, 공통 암부 상승 마스크 축소, 전체 해상도 WB/CCM 렌더를 수행합니다. 기준 영향은 최소 0.5, 추가 상승은 최대 0.35EV입니다. 불확실·검정·포화·이동·반복 확인되지 않은 세부는 기준으로 돌아갑니다. 채택된 상승이 없으면 기준 RAW 픽셀을 유지합니다. 학습 질감 생성·강한 선명화는 없으며 교정된 실제 센서 MSE/SNR 보장이 아닌 보수적 경험 추정입니다.

처리 전에 완전한 비공개 기준 DNG를 영속 저장합니다. 일반 출력은 EXIF 방향을 담은 JPEG97 1개이며 물리 색 메타데이터 누락·렌더 실패는 기준 DNG 1개로 대체합니다. 저장 실패 시 비공개 복구 입력을 보존합니다. UUID·소유자 범위의 멱등 공개 저장으로 재시도 시 JPEG+DNG 중복을 막습니다. SER OFF는 기준 RAW 한 장만 렌더합니다. 당시 최근 사진 버튼에는 JPEG만 전달했습니다. 갤러리 전체 권한·탐색은 추가하지 않았습니다.

## 소스와 검사

- 앱: `photon/night/`의 화면·수명·메타데이터·저장·기록.
- 획득: `photon/raw/RawBurstCamera.kt`, `NightCaptureTiming.kt`.
- 네이티브: `ser_night.*`, `ser_render.*`, JNI 연결·호스트 검사.
- GPU: `GpuSerNight.kt`, 계약은 `NativeSerNight.kt`, `NativeSerRender.kt`.
- 기기: `SerNightGpuDeviceTest`, `SerNightStoreDeviceTest`, `NightSessionDeviceTest`, 선택적 헤더 전용 `SerNightSavedTest`.
- 합성 검사는 생성 데이터와 자체 UUID 결과만 사용·삭제합니다. 미리보기 검사는 셔터를 누르지 않으며 검증 과정에서 실제 사진 픽셀을 읽거나 내보내지 않습니다. 이후 사용자가 따로 허용한 사진 검토는 아래에 구분했습니다.

## 최초 검증

최초 통합 빌드는 서식, 디버그·릴리스 lint(오류 0), 디버그·서명 없는 릴리스·일치 테스트 APK, JVM151회, 네이티브7개를 통과했습니다. 연결 휴대폰에 설치했고 격리된 저장·기록·복구3개, Night 미리보기·재열기1개가 통과했습니다. 두 미리보기 순환에서 물리5, 4080x3060, WB 게인·CCM을 확인했지만 장면의 AWB/AF가 계속 수렴 중이므로 이것만으로 셔터 준비를 증명하지 않습니다.

최초 GLES 비교는 RGB 오차≤1에 실패했습니다. 소형/전체 입력 최대 오차가 7/12 코드값이었으며 그 전에 RAW/EV/마스크는 통과했습니다. 방향 보간의 CPU/GPU 부동소수점 동률 문제를 재현해 양쪽을 수정했습니다. 이후 생성 소형 입력15개·전체4080x3060이 RAW/EV 완전 일치, 마스크 동일, RGB≤1로 통과했습니다. 전체 GPU438ms는 진단 RAW 읽기·정리를 포함하고 네이티브 준비는317ms입니다. 셔터 시간이 아닙니다. 첫 실패는 `device-ser-gpu-before-fix.log`에 남았습니다. 기존 AUTO/HDR/저장/RAW/실시간 미리보기17개, 디테일/UI2개도 통과했으며 UI는 픽셀·썸네일을 숨긴 12배치입니다.

### 수정판 1 실제 촬영: 색 문제와 중단된 시간 표본

사용자는 밝은 곳·어두운 곳의 부자연스러운 색을 보고했습니다. 앱 자체 기록3개는 각각 전체4080x3060 GPU JPEG1개를 보여주지만 다음 준비는3395/32863/791ms, 획득+복원은490/386/446ms였습니다. 추가 터치1회는 UI 확인과 요청 사이 AF 재시작으로 센서 제출 전에 실패했습니다. 791ms 촬영은 SER가 실제 적용됐고 상승 셀283566개, 나머지2개는 기준 픽셀 유지였습니다. 최종 저장1162/860/1001ms는 준비 시간의 대체값이 아닙니다. 헤더 검사는 긴 표본의1200ms 조건을 올바르게 실패 처리했습니다.

사용자는 촬영 사이 갤러리를 열었다고 확인했습니다. 준비에는 재개된 열린 미리보기가 필요하므로 해당 시간에 뷰어·수명 중단이 포함돼 AF/AWB나 처리만의 비용으로 볼 수 없습니다. 분리된 지연은 알 수 없습니다. 시간을 초기화하거나32.9초를 계산·AF 시간으로 단정하면 안 됩니다. 791ms 표본은 목표를 충족하지만 중단 없는 수정판2의 연속2회·시각적 색 검토는 여전히 필요했습니다. 사진 픽셀은 검사·내보내지 않았습니다.

최초 APK SHA-256은 `339b124e182d5e807f95c9c1edea2f1dcbfa1e6c16132b1b20857e8bccd69ea5`이며 앱·테스트 APK는 `initial-candidate/`에 보존했습니다.

### 수정판 2: 보정과 남은 포화 하이라이트 결함

Night 복원은 검증된 초점·WB를 첫 촬영부터 최대2초 유지하되 후속 촬영으로 만료 시점을 연장하지 않습니다. AE는 자동이고 일치하는 최신 물리 결과로 복원·준비를 확인합니다. 미리보기를 누르면 즉시 고정을 풀어 다시 초점을 맞추며 만료 때도 연속 초점·WB로 돌아갑니다. 같은 장면의 불필요한 재획득을 줄이기 위한 짧고 명시적인 연속성 구간이며 미확인 복원을 허용하는 것이 아닙니다.

렌더러는 물리 프레임의 잔여 렌즈 음영 맵을 WB 전에 적용하고 CCM 뒤 RGB 채널별 자르기를 피합니다. 음의 색역 밖 값은 밝기 축으로 압축하고 범위 밖 하이라이트는 공통 RGB 배율을 사용합니다. 유효한 색역 안 값은 유지합니다. 음영 정보가 없거나 미지원이면 교정을 발명하지 않고 DNG를 보존합니다. 확인된 처리 누락을 수정한 것이며 픽셀 검토 없이 실제 시각적 원인을 확정할 수는 없습니다. 하드웨어가 이미 일부 음영을 처리했다고 보고해도 [Camera2 음영 맵 계약](https://developer.android.com/reference/android/hardware/camera2/CaptureResult#STATISTICS_LENS_SHADING_CORRECTION_MAP)에 따라 잔여 맵을 적용해야 합니다.

수정판2는 JVM154회, 네이티브7개, 기기26개를 통과했습니다. 소형 GPU15개, 색역·음영 방향12개, 17x13 맵을 적용한 전체4080x3060에서 RAW/EV 완전 일치·RGB≤1을 확인했습니다. 진단 추가 읽기 포함 GPU528ms입니다. 사용자 촬영의 다음 준비는443/697ms였지만9,137ms 기록1개는 갤러리·수명 중단과 분리되지 않았습니다. 실제17x13 음영 게인1..2.67과 물리 WB/CCM이 있습니다.

사용자는 흰색이 여전히 보라색이라고 보고했고 최근 JPEG2개 열람을 명시적으로 허용해 첨부했습니다. 그2개만 검사했습니다. 물체·어두운 영역은 대체로 중성이지만 밝은 디스플레이 영역은 분홍색이어서, 포화 RAW를 WB로 증폭한 뒤 공통 하이라이트 배율을 적용할 때 생길 수 있는 현상과 맞았습니다.

실제 첫 메타데이터 WB[2.0976562,1,1,1.5957031]·CCM에서 동일하게 완전 포화된 RAW는 선형[2.774,0.569,2.147]이 됩니다. 최댓값 정규화가 잘못된 자홍 비율을 보존합니다. 반대로 포화되지 않은 올바른 중성 입력은 약[1.008,1,.992]입니다. GBRG 배치·행렬 방향은 맞으며 사진·메타데이터 어느 쪽도 다른 CFA를 하드코딩할 근거가 아닙니다.

### 수정판 3: 완전 포화 흰색 보호

음영·WB 전에 각 Bayer 셀의 원본 RAW4개 여유를 검사합니다. **모두** `max(4 DN,0.005*(white-black))` 안에 있을 때만 연속 신뢰도로 최종 선형 RGB를 중성 흰색 쪽으로 이동합니다. 충분한 여유가 있는 채널1개가 있으면 색을 유지하고4개 완전 포화는 흰색이 됩니다. 매우 좁은 포화 근처를 의도적으로 탈색하는 정책이며 부분 포화의 원래 색이나 날아간 세부를 복원하지 않습니다. 실제 WB/CCM의 생성 완전 포화·좁은 전환·비포화 방향·부분 포화 보존 입력과 CPU/GPU 일치를 검사하며 추가 프레임·공간 흐림은 넣지 않았습니다.

수정판3 기록은 `pipelineRevision=3`이며 당시 헤더 검사도 새 수정판3 표본을 요구했습니다. 현재 수정판4 검사 기준은 아래와 같습니다. 첫 실제 준비 전에 카메라가 닫히면 경과 시간을 초기화하지 않고 기록하여 중단 표본을 지속 촬영 검증에서 거부합니다. 동의받은 일회성 흰 종이 집계 탐색을 준비했지만 비동기 활성화 상태가 지속되지 않아 집계를 수집하지 못했습니다. 사용자 사진으로 대신했고 임시 탐색 코드는 제거했습니다. 일반 촬영은 진단 영역 통계를 모으지 않습니다.

수정판3은 JVM154회, 네이티브7개, 디버그·릴리스 lint 오류0/경고16/제안3을 통과했습니다. 전체 기기는27/28로 RAW 재열기1개가 카메라 오류2(동시 카메라 과다)를 보고했습니다. RAW 세션2개를 따로 다시 실행해2/2 통과했지만 깨끗한28/28 실행은 아닙니다. 전체 해상도 합성 GPU는 RAW/EV 완전 일치·마스크 동일·RGB≤1, 진단 읽기·정리 포함380ms로 통과했습니다.

사용자 수정판3 촬영2개는 헤더·준비 검사 통과: 다음 준비391/697ms, 저장902/948ms, 4080x3060 앱 소유 완료 JPEG 각1개, GPU156/148ms. 준비 전 카메라 종료 표식은 없습니다. 첫 촬영은 SER OFF·1장, 두 번째는 SER ON·3장이지만 보조 프레임을 합성 근거가 거부했습니다. 따라서 ON/ON 쌍이나 새 실제 SER 상승의 증거가 아닙니다. 픽셀은 읽지 않았고 사용자가 보라색 잔존을 보고해 수정판3은 **시각적으로 수용되지 않았습니다**. APK는 `revision3-candidate/`, 설치 SHA-256은 `6c834b1816838ee54fdd0b64364d77b02dfd344902b127001bfe3dccfca81ade`입니다.

### 수정판 4: 최초 채널 포화 처리

4채널 모두 포화될 때의 보호는 중성 장면에서 한 채널만 물리 포화되는 경우를 놓칩니다. 측정 WB에서 최초 채널 포화의1.4배 중성 노출은 정규화 센서 RGB 약[.6674,1,.8774]로 녹색만 포화됩니다. WB 뒤 [1.4,1,1.4], 이전 CCM·최댓값 배율 출력은 약[248,182,255]입니다. 행렬이 선형이라 CCM 전 공통 배율만으로 해결할 수 없습니다. 이는 남은 실패 양상을 설명하는 생성 예이며 최근 사진 픽셀의 측정은 아닙니다.

수정판4는 같은 좁은 RAW 여유에서 채널별 포화 신뢰도의 최댓값을 씁니다. 그 증거가 있을 때만 보간·WB·LSC 이후 카메라 RGB를 CCM 전에 `min(rgb,C)`로 접근시킵니다. `C=min_i(LSC_i*WB_i)`는 원본 Bayer4개 위치의 최초 물리 채널이 갖는 보정 후 포화 상한입니다. 모든 위치를1로 가정하지 않고 국소 LSC를 포함합니다. 신뢰도0이면 기존 결과를 정확히 보존합니다. 전역 색상·흰색 분류기, 흐림, 새 노출·추가 프레임은 없습니다. 완전 포화용4채널 보호도 유지합니다.

이는 렌더 정책입니다. 포화된 유색 하이라이트의 색은 달라질 수 있으며 같은 노출 표본만으로 원래 색을 복구할 수 없습니다. C<1이면 흰색을 강제하기 위해 노출을 발명하지 않고 회색 하이라이트를 남길 수 있습니다. 모든 장면 색 정확성·잃어버린 세부 복원 주장은 아닙니다. [Camera2 색 보정 계약](https://developer.android.com/reference/android/hardware/camera2/CaptureResult#COLOR_CORRECTION_TRANSFORM)의 물리 WB→CCM 순서를 유지합니다. 비포화 입력·암부 합성·기존 AUTO/RAW/HDR은 변경하지 않았습니다.

기록·EXIF로 수정판4를 구분하고 실제 사진 검사는 새 쌍의 각 사진에 SER ON을 요구합니다. 서식, JVM154회, 네이티브7개, 디버그·릴리스 lint 오류0/경고16/제안3, 디버그·서명 없는 릴리스·테스트 APK, 대상 GPU·저장 기기9개가 통과했습니다. 초기 서식 실패는 긴 중첩 검사 입력이 원인이었으며 규칙을 억제하거나 검증을 약하게 하지 않고 이름 있는 입력 함수로 나눴습니다.

생성 중성 노출 .7..2.5는 CFA4배치, 중앙·모서리 음영, 실제 WB/CCM 및 서로 다른 녹색·낮은 게인 WB를 다룹니다. 호스트 중성 채널 차이는 최대2 코드값, 일치하는 기기16개는 CPU/GPU RGB≤1로 통과했습니다. 무작위 비포화 RGBA393216바이트를 이전 정책과 정확히 비교했습니다. 유색 포화는 강제 흰색 대신 색을 유지합니다. 전체4080x3060 기기 입력은 실제 WB/CCM,17x13 LSC, 부분·전체 포화64행을 포함합니다. RAW/EV 완전 일치·마스크 동일·RGB 최대 오차1, 진단 추가 읽기·정리 포함 GPU302.424ms입니다. CPU 준비381ms·합성4540ms는 합성 진단이며 제품 GPU 경로나 카메라 준비 시간 측정이 아닙니다. 로그는 `gpu-agent/partial-clip/`, `device-ser-r4.log`입니다.

## 한계

단순 방향성 보간은 CFA·색 흔적을 남길 수 있습니다. DSLR급 화질이나 세계 최초 알고리즘을 주장하지 않습니다. 실제 저조도 질감·색·후광은 사용자 시각 평가가 필요합니다. GPU 소규모 벤치마크는1200ms 다음 셔터를 증명하지 못합니다. 센서·AF 콜백, ISO 한계, 발열, 저장, 제한된 대기열을 실제로 측정해야 합니다. 현재 노출된 Camera2 최대는12.48MP이며16MP 확대 보간 모드는 없습니다. 언급한 APK·사진·로그 경로는 보존된 로컬 자료이며 공개 저장소 첨부를 뜻하지 않습니다.
