# PHOTON 0.8.0 선택적 DetailGuard

2026-10-23. `0.8.0-detail-debug`/코드 14를 연결된 휴대폰에 설치했습니다. 아래 시간은 사용자가 직접 촬영한 결과입니다. 실제 사진 픽셀은 검사하지 않았으며 시각적 평가는 대기 중입니다.

## 동작과 선택 이유

AUTO의 기존 TextureGuard 아래 선택적 디테일 스위치를 추가했습니다. 기존 텍스처 처리 뒤 적용하고 같은 최종 JPEG97 인코딩으로 JPEG 1개만 공개 저장합니다. HDR·RAW·카메라 획득·준비 상태·대기열 규칙은 유지합니다. 설정은 작업별로 복사해 재저장 때도 유지하며 상위 처리 스위치를 끄면 이 단계도 실행하지 않습니다.

새 단계는 근거가 있는 국소 평탄 영역의 밝기 노이즈를 줄이고, 제한된 연속 경계만 강화합니다. RGB 채널 간 차이를 유지하며 채널별 변경은 2 이하입니다. 선명화로 새 국소 밝기 극값을 만들지 않습니다. 암부·하이라이트 보호, 원본만을 읽는 판단, 불투명 이웃 검사와 2픽셀 테두리 보존을 적용합니다. 정확한 정수 계약은 [DetailGuard 사양](PHOTON_DETAIL_SPEC.md)에 있습니다.

초기 검사에서 희미한 선·직조·글자 손실과 더 강한 무작위 노이즈의 소폭 증가를 발견했습니다. 그 후보는 설치하지 않았습니다. 수정은 매우 약한 대비와 연속 선을 보존하고 선명화 전에 평행 경사를 확인합니다. 이전 실패 기록도 출력 폴더에 남겼습니다. 합성 입력만으로 모든 실제 질감 보존을 증명하지는 못합니다.

## 처리와 시간

두 번째 GPU 계산 단계는 기존 EGL 문맥과 업로드 버퍼를 재사용하고 마지막에 한 번 동기화·읽기합니다. 텍스처·디테일 변경 수는 별도입니다. 실행 제출 시간은 CPU의 명령 제출 시간이며 개별 GPU 실행 시간이 아닙니다. 큰 영상은 GLES, 작은 영상·미지원 사례는 네이티브 CPU를 사용합니다. 상주 작업자나 NPU 모델은 없습니다.

목표는 셔터 누름부터 다음 사진을 허용하기까지 1,200ms 이하입니다. 최종 저장 완료와는 별개이며 2개 작업 대기열이 가득 차면 다음 촬영이 늦어질 수 있습니다. 커널 시간 대신 대기열 압력을 포함한 실제 `shutterReadyMs`를 측정해야 합니다.

## 검증 결과

수정된 호스트 커널은 대비 2/3/4/5/6/7/8/12의 선·직조·H/A 글자 56개 조합을 바이트 단위로 보존했습니다. 단조 경계 6개는 새 극값·역전·먼 후광이 없었습니다. 부드러운 경계의 중앙 3픽셀 평균 경사는 18→18.6667(+3.7%)로 늘었습니다. 무작위 RGBA 47,168픽셀의 원본 기준 구현 일치가 통과했고 채널별 변경은 2 이하입니다.

대신 추가 밝기 노이즈 RMSE 감소는 고정 시드 ±3/5/8 회색 노이즈에서 0.40%/0.41%/0.019%에 그칩니다. 초기의 더 강한 제거기는 노이즈를 더 줄였지만 약한 무늬를 흐려 거부했습니다. 기존 색차 TextureGuard는 유지합니다. 강한 노이즈 제거나 DSLR급 실제 화질의 근거가 아닙니다. 강한 노이즈 입력의 10픽셀은 여전히 선명화에 들어갔지만 전체 RMSE는 늘지 않았습니다.

최종 수정 빌드·디버그/릴리스, JVM 136회, 네이티브 5/5, lint가 통과했습니다(오류 0, 기존 경고 13, 제안 1). 기기 15/15는 저장7, HDR3, 일반 미리보기2, RAW 세션·광학 전환2, 설정 보존1을 포함합니다.

선택적 `DetailDeviceTest`도 `parity_passed`로 통과했습니다. 소형 입력 72개와 4080x3060 입력 2개를 검사했고 큰 입력은 각 3회 반복했습니다. 모든 바이트와 두 변경 수가 순차 네이티브 TextureGuard+DetailGuard와 일치하며 입력을 보존했습니다. 기존 detail=false 출력도 일치합니다. 준비된 GPU의 두 단계 합계는 노이즈168ms/부드러운 경계160ms, CPU는 613/438ms였습니다. GPU에는 설정·업로드·읽기·정리가 포함됩니다. 첫 호출은 217/157ms로 드라이버 캐시가 이미 준비됐을 수 있습니다. 합성 처리 성능이며 실제 셔터 시간이 아닙니다.

통합 합성 JPEG 저장은 디테일 OFF261ms/ON440ms, 모두 최종 결과 1개였습니다. 필터는 126→160ms였지만 ON은 253,102픽셀을 바꿔 JPEG97로 다시 인코딩했고 OFF는 변화가 없어 원본 JPEG를 재사용했습니다. 전체 차이를 GPU 비용으로만 설명하면 안 됩니다. 방향·ISO 메타데이터, 상위 스위치 OFF의 바이트 보존, 비공개 입력 정리를 통과했습니다.

## 사용자가 직접 촬영한 휴대폰 결과

HDR OFF, TextureGuard·DetailGuard ON입니다. 두 기록 모두 `gpu_gles31`, detailApplied=true, 최종 JPEG 1개입니다. 다음 셔터는 **936/785ms**로 모두 1,200ms 이내였습니다. 처리·저장은 384/362ms, 총 완료 1,324/1,150ms로 셔터 목표와 별개입니다. 누름 사이가 7.3초여서 가득 찬 대기열에서의 지속 연사를 증명하지 않습니다.

GPU 두 단계와 전송을 포함한 필터는 122/138ms, 디테일 변경은 178,540/207,393픽셀이었습니다. 변경 수는 진단값이지 시각적 개선의 증거가 아닙니다. 두 정확한 기록 URI에서 결과 1개, JPEG 크기·방향, 0보다 큰 크기, 소유 패키지, MediaStore 저장 완료를 헤더 검사로 확인했습니다. 사진 픽셀을 읽거나 내보내지 않았습니다.

1.2초 목표는 이 2회에서 통과했으며 모든 초점·조도·발열·대기열 조건의 보장이 아닙니다. 실제 시각적 보존은 사용자 평가가 필요합니다. 이전 버전과 원본 사진은 유지했습니다.
