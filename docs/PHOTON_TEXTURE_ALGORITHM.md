# PHOTON 질감 보호 알고리즘 — 설계 및 v0.1 실험 구현

> 0.7.0 저장 정책 변경: 새 AUTO 촬영은 최종 JPEG 한 장만 공개한다. 질감 수식은 유지하며,
> HDR과 함께 켜면 합성 후 질감 처리를 거쳐 한 번만 JPEG97로 재인코딩한다. 촬영 입력은
> 성공 시 삭제되는 앱 내부 임시 파일이며 기존 사진에는 손대지 않는다. 현재 설계/지연 기준은
> [PHOTON_AUTO_HDR](PHOTON_AUTO_HDR.md)를 참조한다. 아래 원본+결과 정책은 0.5/0.6 이력이다.

2026-10-23. 사용자 선택: **자연스러운 질감·과보정 억제**.
최초 앱 버전: 0.5.0-texture-experiment. 알고리즘 버전: texture-guard-0.1.
0.6.0에서는 같은 수식을 네이티브로 실행한다. Kotlin 구현은 비교 기준으로 유지한다.

0.7.5 AUTO는 8MP 이상 사진에 GLES 3.1 compute shader를 사용한다. 같은 질감 판단과
반올림을 정수식으로 옮겼으며, 전 범위 수치 검사와 인공 영상의 CPU/GPU 픽셀 일치 검사를
통과했다. 입력은 읽기 전용이고 결과 버퍼를 따로 만들기 때문에 GPU 오류가 나도 CPU로
다시 처리할 수 있다. 작은 영상은 초기화·전송 비용을 피하도록 CPU를 유지한다.
GPU는 매번 같은 호출 스레드에서 열고 닫으며 상시 작업자나 서비스가 없다.
실측 시간은 [v0.7.5 검증](PHOTON_075_VERIFICATION.md)을 참조한다. NPU는 사용하지 않는다.

0.8.0은 기존 처리를 유지한 채 선택 가능한 ‘디테일 강화’를 추가했다. 약한 대비·반복선·
글자 구멍을 보존하고, 옆으로 이어지는 경계에만 최대2단계의 윤곽 보정을 적용한다.
디테일 보존을 우선해 추가 밝기 노이즈 제거 강도는 매우 약하다. 기존 색잡음 처리와
새 처리의 GPU 업로드·결과 회수는 공유한다. [계약과 검증](PHOTON_080_VERIFICATION.md)을 참조한다.

## 목적과 독자성의 범위

목표는 다른 카메라의 색감/샤프닝을 재현하는 것이 아니라, **변경할 근거가 충분할 때만
변경하고 근거가 약하면 원본을 선택하는 카메라**다. 과도한 평탄화와 가짜 윤곽을 피한다.
고유한 부분은 방향별 합의, 밝기 구조 보호, 색 변화 상한, 원본 보존 및 향후 시간축
증거를 묶는 PHOTON의 의사결정 규칙이다. 특정 카메라의 구현/가중치/룩을 복제하지 않았다.

색차 분리, 이웃 비교, 정합, 강건 통계 자체는 공통 영상처리 지식이다. 이 조합이
학술적으로 최초라거나 특허상 신규하다고 주장하지 않는다. 단일 프레임에서 잡음과
미세한 색 질감을 항상 정확히 구별할 수 없다는 한계를 설계의 출발점으로 둔다.

## 현재 입력과 사용자 계약

현재 AUTO 입력은 **제조사 ISP가 처리한 JPEG**다. 앱 후처리 OFF는 이 JPEG를 재디코딩/
재인코딩하지 않고 그대로 저장한다는 뜻이다. 제조사 노이즈 제거/샤프닝까지 껐다는 뜻은
아니다. Camera2의 NR/EDGE OFF는 별도 지원 조회와 CaptureResult 실측이 필요하고,
RAW 역시 lens shading 등 기기 처리가 적용됐는지 메타데이터로 확인해야 한다.

- 기본 OFF. 사용자가 고른 ON/OFF는 로컬 설정에 저장한다.
- ON도 카메라 원본을 먼저 저장한다. 처리본은 같은 capture ID의 `_TEXTURE.jpg`로 추가한다.
- `_ORIGINAL.jpg`는 읽기 전용이다. 실패/취소/메모리 부족 시에도 삭제하거나 덮어쓰지 않는다.
- 바뀐 픽셀이 0이면 재압축을 피하고 원본만 유지했다고 알린다.
- 현재 처리는 **저장 사진에만** 적용한다. 프리뷰는 원본 CameraX 영상이며 UI에 명시한다.
- 밝기 자동 상승, HDR 톤 매핑, LUT, 선명화, 초해상도는 v0.1에서 하지 않는다.
- 처리 중 셔터·설정 변경을 막고, 촬영 시점의 ON/OFF를 그 사진에 고정한다.
- JPEG와 처리본 비교 시 재압축 손실까지 평가한다. 알고리즘 픽셀 검사만으로 저장 화질
  향상을 주장하지 않는다.

## v0.1: 방향 합의에 따른 제한적 색잡음 보정

기준 코드: `app/src/main/kotlin/dev/lunacam/app/photon/TextureGuard.kt`.
현재 실행 코드: `native/lunacore/src/texture_guard.cpp`.
3행의 원본 RGBA를 캐시하고 AndroidBitmap을 한 번 잠가 JNI 왕복과 Kotlin 픽셀 루프를
줄인다. O3를 사용하지만 fast-math와 부동소수점 결합을 금지해 기존 판단을 유지한다.
입력: sRGB로 디코딩한 8-bit RGB. JPEG의 감마 부호화 공간에서 작은 색차만 조정한다.
RAW 센서 잡음 모델을 이미 가공된 JPEG에 그대로 적용하지 않는다.

### 1. 밝기와 색차 분리

```
Y  = (R + 2G + B) / 4
Co = (R - B) / 2
Cg = G - Y
R = Y - Cg + Co; G = Y + Cg; B = Y - Cg - Co
```

여기서 Y는 계산용 근사 명도다. scene-linear 휘도, 물리적 광량 또는 지각 명도와
동일하지 않다. v0.1은 이 Y의 공간 구조를 그대로 두고 색차만 제한적으로 수정한다.

### 2. 수정 대상인지 먼저 판정

3×3 창에서 수평/수직/두 대각선의 반대쪽 픽셀을 네 쌍으로 나눈다.

- 3×3 전체 Y 범위가 10 code values보다 크면 경계/질감으로 보고 원본 유지.
- 중심 Y가 [16,239] 밖이면 원본 유지. 불투명 픽셀만 처리.
- 각 쌍에서 `|ΔY|≤6`, `|ΔCo|≤6`, `|ΔCg|≤6`일 때만 그 방향에 투표권을 준다.
- 4방향 중 3방향 이상이 유효해야 한다.
- 유효 방향들의 색차 평균이 서로 일치해야 한다: Co 범위≤4, Cg 범위≤3.
- 합의 색차와 중심의 차이가 어느 성분이든 12보다 크면, 색 경계/미세 색 물체일 수
  있으므로 처리하지 않는다.

이 조건들은 **현재의 보수적인 실험 상수**이며 S25 Ultra 전체 장면에 최적화됐다는
근거가 없다. 실제 저조도/JPEG 압축 패턴에서는 수정이 적거나 잘못된 판단이 있을 수 있다.

### 3. 정수 변화 예산

합의 평균과 중심의 차이를 `eCo`, `eCg`라 하면:

```
dCo = clamp(round(0.35 × eCo), -2, 2)
dCg = clamp(round(0.35 × eCg), -1, 1)
R' = R + dCo - dCg
G' = G + dCg
B' = B - dCo - dCg
```

RGB 범위를 벗어나면 clamp로 색을 왜곡하지 않고 원본을 선택한다.
이 식은 **JPEG 재인코딩 전** `R'+2G'+B' = R+2G+B`를 정확히 유지하며, 각 채널의 변화는
최대 3 code values다. 회색의 미세 명암을 직접 흐리거나 증폭하지 않는다.
JPEG 재인코딩 후에는 이 두 수치가 보장되지 않는다. 따라서 원본을 항상 제공한다.

### 4. 메모리와 실패 경계

- O(width×height), 반경 1, 반복 필터링 없음. 결과를 다음 입력으로 다시 쓰지 않는다.
- 가변 Bitmap 하나와 입력 3행/출력 1행만 사용. 4080×3060 ARGB bitmap은 약 47.6 MiB,
  행 버퍼는 약 64 KiB. JPEG 디코더/인코더와 앱 메모리는 별도이며 이 숫자는 피크가 아니다.
- 픽셀마다 반복되는 채널 추출은 inline하여 개발 빌드의 함수 호출 비용을 줄였다.
  최종 기기 합성 저장 경로는 약 9.1초였다. 연사 성능이나 다른 장면의 시간을 보장하지 않는다.
- 16 MP 초과 또는 HDR gain map 입력은 원본 유지로 실패 처리. 조용히 축소하지 않는다.
- 0.5.0은 각 행에서 취소 및 15초 경과를 확인했다. 0.6.0은 JNI 전후에 취소를 확인하며
  필터/decode/encode 도중 즉시 중단이나 15초 전체 실행시간 상한을 보장하지 않는다.
- 처리본은 새 MediaStore IS_PENDING 행에 기록하고 EXIF를 쓴 뒤에만 공개한다.
- 실패 시 이번 호출이 만든 미완료 처리본만 삭제한다. 원본은 삭제 대상이 아니다.
- EXIF는 방향/날짜/노출/초점거리 등 허용 목록만 복사. GPS/MakerNote/일련번호는 복사하지 않는다.

## 어떤 장면에서 이득/손해가 가능한가

예상 이득: 명암 변화가 적은 실내 벽/그늘에서 약한 붉은·푸른 색 얼룩을 소폭 줄일 가능성.
이는 가설이며 실제 장면 검증 전에는 제품 품질 주장으로 사용하지 않는다.

보존 목표: 풀·머리카락·옷감의 명암 패턴, 피부의 작은 명암 변화, 색 경계, 하이라이트.
한계: 미세하고 저대비인 실제 색 점/색 질감은 잡음과 구분되지 않아 조금 약해질 수 있다.
이미 ISP에서 뭉개진 디테일이나 날아간 하이라이트는 복구할 수 없다.

## 시간축 증거로 처리량 결정 (0.5.0의 설계, 0.6.0에서 제한적 구현)

다음 6단계의 현재 구현과 차이는 [PHOTON_RAW_ALGORITHM.md](PHOTON_RAW_ALGORITHM.md)에 있다.
전역 짝수 픽셀 정합만 사용하며 subpixel/회전/국소 warp 및 RAW 현상은 범위 밖이다.

v0.1의 작은 JPEG 보정을 최종 화질 엔진으로 과장하지 않는다. 본격적인 개선은
동일 장면을 여러 번 관측할 수 있는 RAW/선형 데이터 기반의 다음 연구 단계다.

1. **보존할 기준 프레임 선택**: 짧은 노출·흔들림·포화 마스크를 비교해 기준을 선택한다.
   기준 원본과 노출/감도/타임스탬프/색 보정 데이터를 재생 가능한 묶음으로 보관한다.
2. **정합 실패를 먼저 찾기**: forward/backward 정합 일관성, 가림, 움직임, 포화,
   노출 정규화 오차로 픽셀별 사용할 수 없는 관측을 제거한다.
3. **질감의 재등장 측정**: 같은 위치의 미세 명암/색차 패턴이 정합된 프레임과 여러
   공간 크기에서 같은 방향/부호로 다시 나타나는지 검사한다. 반복 관측되는 성분을
   디테일 후보로, 일관되지 않은 성분을 불확실 성분으로 구분한다.
4. **합성/보존 중 선택**: 좋은 프레임 수가 적거나 판단이 모호하면 기준 프레임으로
   돌아간다. 정합 신뢰도×비포화 신뢰도×노출별 잡음 역분산을 가중치로 사용하되,
   유효 표본 수 `N_eff=(Σw)²/Σ(w²)`가 작으면 병합 강도를 줄인다.
5. **변경 예산 부여**: 기준 대비 밝기/색/경계 이동량을 제한한다. 강한 밝기 들어올리기보다
   자연스러운 노출과 하이라이트 분리를 우선한다. 목표를 충족하면 더 처리하지 않는다.
6. **부분 실패는 부분 fallback**: 움직이는 얼굴은 기준 한 장, 정적인 벽은 여러 장처럼
   구역별로 선택한다. 경계에서 가중치를 연속화하며, halo/ghost를 검사한다.

0.5.0에는 전용 Camera2 capture 경로가 없었다. 0.6.0에서는 사용자 요청으로 별도 RAW
세션과 burst를 추가했으며 기존 AUTO를 교체하지 않는다. HDR과 AI 학습은 추가하지 않았다.
NR/EDGE는 지원되는 OFF를 요청하며 실제 촬영 결과를 영수증에 기록한다.

## 공식 근거

- [CameraControl](https://developer.android.com/reference/androidx/camera/core/CameraControl):
  핀치에는 setZoomRatio, 슬라이더에는 setLinearZoom. 연속 요청의 이전 future 취소는 정상.
- [Android 드래그·크기 조절](https://developer.android.com/develop/ui/views/touch-and-input/gestures/scale):
  ScaleGestureDetector 사용. 멀티터치 뒤 마지막 손가락 해제를 초점 탭으로 처리하지 않는다.
- [CameraMetadata](https://developer.android.com/reference/android/hardware/camera2/CameraMetadata):
  제조사 처리 설정은 지원 여부와 결과 메타데이터를 확인해야 한다.

실제 구현/빌드/기기 결과는 `PHOTON_TEXTURE_VERIFICATION.md`에 별도로 기록한다.
